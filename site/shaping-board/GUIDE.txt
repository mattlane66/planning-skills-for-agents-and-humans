# Shaping Board

Optional browser surface for **Planning Skills for Agents and Humans**. The board supports flexible exploration; the canonical Markdown and human commitment gates remain authoritative.

## Start

- Hosted (after merging and deploying): https://mattlane66.github.io/planning-skills-for-agents-and-humans/shaping-board/
- Offline: download `index.html` and open it in a browser. No server, account, external assets, or API calls required unless you explicitly enable the optional status feed (which needs HTTPS/CORS).
- **Example** loads a DWC Requests sample. The GitLab alternatives A–C are marked as placeholder sketches; none is claimed to be proven.
- **New** creates a blank board. **Import** accepts exported `.board.json`. Save a project by **Export JSON**, then commit the file in your project's own repo. Browser autosave is convenience, not version control.

## Open your own existing planning project

From the Planning Skills repository, run:

```bash
python3 scripts/build_shaping_board_data.py \
  --planning-dir /path/to/product/planning \
  --output /path/to/product/planning/shaping.board.json
```

Then open the board and import that file. The adapter reads the project's existing frame/shaping files and available breadboard tables. It does not modify Markdown, invent a missing breadboard, or confer acceptance. Where a candidate lacks a diagram, it is deliberately left as a placeholder until shaped. The board shows accepted input information from existing artifacts, but is an **inspection/editing copy** and is not a replacement for those artifacts.

For a brand-new project, use the board directly; it exports a ZIP containing a working frame, working shaping document, and *all* candidate-shape breadboards. These are starting points for review, not authorized tasks. Use the normal repo skills to reconcile selected-design intent and choose a build slice. For an existing project, **review the proposal diff and merge deliberately**: do not overwrite higher-authority accepted Markdown wholesale. The board does not provide automatic lossless Markdown round-tripping.

## What's inside

- **Frame:** problem and outcome, Appetite, cut line, authority
- **Stories:** per-option traces; a complete supported trace requires connected, existing nodes and links
- **Paths / Compare:** diagrams created from place, action, store, and decision node notation
- **Fit check:** exploratory ✓/◐/×/? ratings, stable requirement IDs, independent requirement status and acceptance; ZIP fit is binary because unproven claims cannot pass the repo's formal check
- **Trade-offs:** promises, accepted risks and cuts, working preferred option
- **Things:** working product nouns, stable IDs, likely system ownership
- **Human selection:** requires accepted requirements, Appetite, explicit cut line, resolved mandatory fit, and rationale
- **Plan, Review, Release:** working notes and evidence bookkeeping. These tabs do not implement code, run tests, authorize work, or verify a deployed product.

## Board diagram text

```text
group: Account screens = P1 U1
P1 | place | Account page | display current status | app
U1 | action | Confirm action | click confirm | UI
N1 | action | Validate request | reject invalid changes | backend
S1 | store | Account state | read and write status | db
P1 -> U1 : use
U1 -> N1 : submit
N1 -> S1 : save
```

Optional `@x,y,w,h` node placement and SVG route data use numeric positioning. Broken references, duplicate node IDs, missing story links, and unrecognized graph lines should be corrected before a decision is accepted.

The editor is text-first to avoid a heavyweight canvas dependency. The same board works across devices; on a narrow screen, scroll to inspect large diagrams rather than expecting microscopic cards.

## Authority and scope

The board's JSON is an editable working snapshot. The repository's `shaping/SKILL.md`, `breadboarding/SKILL.md`, `shaping/references/fit-checks.md`, human-decision gates, and acceptance rules control actual downstream scope. An accepted shape alone **never** promotes an exploratory candidate breadboard into selected-design intent. Accepted selected-design reconciliation and an explicitly selected slice are separate steps.

The Product Intent Layer and code-drift checks remain separate opt-in tooling. The board's **Things** are *not* accepted invariants or confirmed code mappings and must not be treated as such.

## Product-level drift during implementation

Product Intent is an opt-in extension. After accepting a selected design through the repo's normal human gates, compile the PlanningPackage and run the existing trusted Product Intent gate on changed code. Save its JSON output, including REVIEW and DRIFT reports.

Create a read-only projection for the board:

    python3 product-intent/board_report.py --package /tmp/planning-package.json --gate-report /tmp/product-intent-gate.json --output /tmp/product-status.json

Open Review → Import product status JSON. See affected product invariants and decisions, their referenced requirements, changed implementation paths, approved scenario results, and coverage gaps. Fit Check also marks impacted requirements. These findings do not mutate or accept planning intent.

### Optional automatic status feed

The Review tab can now refresh a **public, trusted-CI-published Product Intent board report** without manual re-import. This remains a read-only projection, not a new product authority or a direct GitHub Actions-artifact downloader.

1. In the **product repository** (not this methods repo), adopt the `product-intent/ci-example.yml` workflow after adapting its planning paths. It runs the trusted gate for PRs and protected `main` pushes, emits the **full 40-character checked commit SHA** as `revision`, and uploads `product-status.json` as an artifact. Preserve the gate's nonzero REVIEW/DRIFT exit code. This example does **not** publish an HTTPS feed itself.
2. If a status report can safely be public, arrange for a **separate trusted publisher operating on the protected main branch** to host a carefully reviewed, non-sensitive status JSON at an HTTPS URL with cross-origin browser access (CORS). Do not let an untrusted PR, its modified workflow, or an agent-authored report publish/overwrite that authoritative URL. Do not publicly publish proprietary source paths, scenario bodies, or sensitive intent. The provided report includes changed paths and scenario identifiers by default; sanitize these in your trusted publication step, preserving verdict, linked requirement identifiers, and each tested scenario's result. If privacy cannot be guaranteed, keep using local file import.
3. In **Review → Automatic product status**, enter the public HTTPS JSON URL, public GitHub `owner/repo`, and protected branch (usually `main`). The report's `product` must match the Board project name. Select **Connect feed**. This configuration is saved locally for the Board project, excluded from exported Board JSON, and never requires a token.
4. The Board checks the public GitHub branch HEAD SHA through GitHub's API and fetches the JSON report when opened, when revisiting the browser tab after five minutes, or when **Refresh now** is selected. A report with a missing or nonmatching full SHA, invalid evidence, or generation time older than 72 hours is **unverified** and cannot show PASS, even if a prior cached report was green. A connection failure also removes the old status from the UI. Other files cannot silently configure an automatic feed through Board import.

**Security/interpretation:** A matching commit and HTTPS URL do not independently authenticate the report's producer or prove that tests ran. The configured publisher and protected CI process must be trusted. Even a legitimate PASS covers only approved, explicitly mapped scenarios—not all software behavior, production health, or post-release effect. GitHub Actions artifacts are not generally readable directly from an unauthenticated standalone browser, and GitHub API rate limits/CORS may prevent refresh. The Board deliberately asks for an explicit public HTTPS feed instead of storing a GitHub token.

The original **Import product status JSON** remains available for offline/private projects and disables the configured automatic feed when used.

PASS covers only explicitly mapped, approved and tested scenarios; REVIEW means uncertain or insufficient evidence, not demonstrated failure; DRIFT is an observed failure of an approved scenario. This is not automatic prediction of all product behavior or post-release outcomes.

## AI Workspace (local-first)

The Board now has **AI Workspace** and **Product map** tabs. AI Workspace prepares provider-aware instructions for Codex, Claude Code, Gemini CLI and other agents, then exports an agent-ready ZIP containing working planning files, `planning/shaping.board.json`, a starter instruction and setup guidance. No model account connection or backend is involved. The user enables Planning Skills in their chosen agent, opens their own product repository there and performs implementation in that environment.

The **Review AI proposal** tool imports a complete schema v3 `.board.json` with the same project ID. It previews changed sections and applies only manually selected sections as Working. Applied changes invalidate selection authority; changed requirements, frame and appetite are de-authorized as appropriate. AI-supplied acceptance claims, verification reports, and release/check statuses do not become accepted facts through this import. The existing **Import** button still replaces the whole working Board; use Review AI proposal for selective revisions.

The **Product map** tab exposes the current working connections among requirements, preferred-shape node references, candidate shapes, product nouns and available read-only Product Intent results. It is not the canonical compiled Product Ontology and must not be used to infer execution coverage.

**Start here:** [AI Workspace guide](../../docs/shaping-board-ai-workspace.md).

## Validation

Run `node site/shaping-board/test-board.mjs` after `cd site && npm ci --ignore-scripts`, plus `python3 -m unittest discover -s tests -p 'test_shaping_board*.py'` from the repository root. CI also checks the documentation portal and repo health.

## Limitations

- The browser does not execute agent skills, connect an AI account, run code, call GitHub for writes, verify source code, prove user outcomes, or promote accepted intent.
- Existing markdown import is a **read-only projection**. Its round-trip export is a reviewable proposal, not a patcher that preserves every unrelated Markdown section.
- Autosave is local to the browser; keep exported JSON in your own repository for durable version history.
- Diagram editing is text-based and not multiuser; deliberately no backend.
