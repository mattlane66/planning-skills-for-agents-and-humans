# Documentation portal deployment and trust model

The repository has one canonical skill and planning-method source, plus several presentation surfaces:

- `site/index.html` is the tracked, self-contained offline documentation portal, reproducibly built from canonical repository content and `site/src/`.
- GitHub Pages serves the regenerated and validated portal, separately staged interactive examples (including the Shaping Board), the Product Ontology projection of an accepted example, review demos, and public policy pages. Hosting does not make these interfaces authoritative.

## Pull requests: read-only validation

`Repo Health` checks pull requests with `contents: read` only. The minimum-Node job installs locked dependencies with lifecycle scripts disabled, runs the deterministic portal checks and Shaping Board tests, rebuilds `site/index.html`, and requires the regenerated bytes to match the tracked file.

When the tracked portal differs, CI uploads the regenerated file and `site-index.patch`. A maintainer must apply the repair to the branch; PR checks never receive write credentials merely to rewrite derived assets. Do not use `pull_request_target` to execute PR code with write authority.

## `main`: trusted build and deployment

`.github/workflows/pages.yml` runs after a `main` push that matches its path filters, or manual dispatch. Its build job:

1. Checks out the trusted `main` commit with no persisted credentials.
2. Installs locked Node dependencies with lifecycle scripts disabled, rebuilds and validates the standalone portal.
3. **Warns rather than blocks Pages deployment** if the tracked `site/index.html` differs from its regenerated output. Repo Health independently fails on that mismatch; the repository should be corrected even if Pages succeeds.
4. Generates the Product Ontology from the canonical Simple Grocery List example; stages the separate Shaping Board and other published pages.
5. Captures a real-browser Shaping Board comparison screenshot for the README and builds the reviewer demo.
6. Uploads the staged site as a Pages artifact.

The separate deployment job holds `pages: write` and `id-token: write` only, and does not execute repository code. The build job is read-only. The screenshot is generated from the actual DWC Requests board; it is not a hand-maintained mockup.

Pages currently depends on the separately configured live reviewer-demo capture. The viewer and planning skills themselves do not require that runtime. If live demo capture fails, inspect the Pages build job before claiming deployment succeeded.

Repository settings should use **Pages → Build and deployment → Source: GitHub Actions**. Branch ruleset enforcement and required checks must be verified independently in GitHub administration; passing CI alone does not prove that `main` is protected.

## Local verification

```bash
cd site
npm ci --ignore-scripts
npm run check
node shaping-board/test-board.mjs
CHROME_BIN=/path/to/chrome npm run test:browser
```

From the repository root, run `bash scripts/check-repo-health.sh` and the Shaping Board Python adapter tests. The real-browser smoke covers direct `file://` opening, keyboard interaction, Mermaid SVG rendering, narrow-screen behavior, and runtime errors. It does not prove complete behavior of external hosted tools, agent integrations, or all application code.
